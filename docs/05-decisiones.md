# Registro de Decisiones

Registro estilo ADR (Architecture Decision Record): cada decisión importante de producto o técnica queda anotada con su razón, para no perder el "por qué" con el tiempo.

| # | Decisión | Razón |
|---|---|---|
| D1 | La app tiene dos superficies: aplicación de usuario final (pública + con login) y back office (gestión). | Separar el consumo de información de la administración. |
| D2 | Ambas superficies son responsive (celular, tablet, PC). | El back office no debe atar al admin a una computadora. |
| D3 | Registro de usuario vía auto-registro (SSO), pero el acceso a contenido por curso se habilita manualmente. | Escalar el alta sin perder control sobre quién ve qué. |
| D4 | Menores de 18 no se auto-registran vía SSO; se pide fecha de nacimiento y, si es menor, la cuenta la crea un admin/discipulador usando contacto de un tutor. | Límite conocido y aceptado (no hay verificación de identidad real, igual que otras apps del mercado). |
| D5 | Se acepta manejar datos que revelan afiliación religiosa (curso, bautismo, ministerio), aunque se use SSO para autenticación. | El SSO delega la autenticación, no evita que el propio sistema guarde estos datos. Pendiente definir política de privacidad antes de un lanzamiento real (no bloquea el MVP). |
| D6 | El modelo de dominio incluye una entidad Sede desde el día uno, aunque hoy exista una sola. | Evitar rediseño si a futuro se suman sedes. |
| D7 | La app complementa, no reemplaza, los canales existentes (WhatsApp sigue activo). | Decisión de reemplazo total queda en manos de la iglesia a futuro. |
| D8 | No se valida el problema con la iglesia antes de construir; se construye un prototipo/MVP primero y se presenta después. | Decisión deliberada del autor: quiere mostrar algo concreto, no vender una idea. |
| D9 | El modelo se piensa por módulos independientes (Bienvenida, Vida Nueva, Vida de Servicio, Ministerios, Eventos). | Permitir crecimiento incremental sin rehacer lo ya construido. |
| D10 | El contenido de un Grupo/Curso permanece disponible después de finalizado. | No tiene sentido ocultar material que la persona ya tenía derecho a ver. |
| D11 | Los roles de una Persona son acumulativos, no se reemplazan entre sí. | Refleja el proceso real: alguien no "deja de ser" Miembro registrado al empezar Vida Nueva. |
| D12 | El discipulador puede ver teléfono y dirección de su discipulado. | Los necesita para coordinar encuentros presenciales, tal como sucede hoy. |
| D13 | Postulación a Ministerio requiere el flag "Apto para Ministerio" (no está abierta desde el primer login) y se implementa con formulario in-app, no derivación a WhatsApp. | Refleja que no cualquiera puede sumarse a un Ministerio sin antes recorrer el proceso (Vida Nueva → Vida de Servicio). |
| D14 | Las postulaciones a Ministerio las revisa el Admin, no un líder de Ministerio propio (por ahora). | Simplicidad para el MVP; puede evolucionar en el futuro. |
| D15 | El subgrupo interno de un Ministerio se llama "Célula" (no "Grupo", para evitar colisión con el concepto de Grupo de un Curso). | Claridad terminológica en el modelo de datos. |
| D16 | Documentación organizada en documentos separados por responsabilidad (no un documento por sesión de trabajo, no un único documento monolítico). | Cada documento tiene una sola razón para cambiar, como en un proyecto de producto real. |
| D17 | Cronograma es una entidad propia (no un atributo simple de Grupo). | Permite modelar múltiples semanas con fechas de liberación de forma flexible. |
| D18 | El Contenido/Material pertenece al Grupo, no al Curso. | Cada instancia (Grupo) puede tener material propio, aunque el Curso sea la misma plantilla. |
| D19 | Una Persona solo puede pertenecer a un Ministerio activo a la vez, con historial de Postulaciones pasadas conservado (no se borran, se marcan "inactiva"). | Refleja la regla real de la iglesia; el historial sirve para trazabilidad. |
| D20 | Un Grupo de Vida de Servicio puede tener varios Líderes asignados (relación varios a varios vía entidad Liderazgo). | Refleja que varios líderes rotan presentando material cada domingo. |
| D21 | Persona tiene un atributo `estado` (activa / pendiente_tutor). El intento de registro de un menor no se descarta: queda visible para el Admin para seguimiento manual. | Permite que el Admin detecte y gestione manualmente casos de menores interesados, sin perder el dato de contacto. |
| D22 | Teléfono, dirección y Sede son obligatorios en el registro inicial (no opcionales para completar después). | Simplifica el modelo: un discipulador puede necesitar esos datos desde el primer momento. |
| D23 | Se deja de usar el nombre propio "Flor" en la documentación; se usa siempre "Admin" como nombre de rol. | El modelo no debe atarse a una persona puntual, aunque hoy sea una sola. |
| D24 | Curso tiene un atributo `modalidad`: `liberacion_programada` (contenido digital, ej. Vida de Servicio) o `seguimiento_por_encuentros` (material físico, ej. Vida Nueva). Se agrega la entidad Encuentro para este segundo caso; Cronograma/Contenido quedan como relaciones opcionales del Grupo, no obligatorias. | El libro de Vida Nueva es físico y se entrega en la primera reunión — no hay nada que "liberar" digitalmente, solo un registro de avance. Se deja la opción abierta por si a futuro se digitaliza el material. |
| D25 | Admin asigna manualmente el discipulador a cada persona que inicia Vida Nueva. | Es quien tiene visibilidad de qué discipuladores están disponibles. |
| D26 | La inscripción a un Grupo de Vida de Servicio es por solicitud de la Persona + aprobación del Admin (no alta directa, no autoservicio sin revisión). | Mantiene control sobre quién entra a cada edición del curso. |
| D27 | El contenido semanal se libera automáticamente solo cuando se cumplen dos condiciones a la vez: la fecha programada llegó Y el contenido ya fue cargado por un Líder. Cualquier Líder asignado al Grupo puede cargar contenido de cualquier semana (no hay responsable fijo por semana). | Evita "liberar" un espacio vacío si el Líder se atrasa en cargar el material; refleja el proceso actual (alguien carga el miércoles lo que corresponde). |
| D28 | El flag "Apto para Ministerio" se activa manualmente por el Admin, a partir de una solicitud simple de la Persona (no un formulario extenso). No hay validación automática de "Vida de Servicio completado" en el MVP — es un criterio que aplica el Admin. | Evita construir lógica de detección automática de finalización de curso, que no está resuelta todavía (ver `06-preguntas-abiertas.md`). |
| D29 | Una Postulación rechazada no bloquea a la Persona de volver a postularse al mismo Ministerio más adelante. | Un rechazo puntual (ej. por timing) no debería ser una condena permanente. |
| D30 | La Célula dentro de un Ministerio la elige la Persona en el formulario de postulación, no el Admin. | Refleja preferencia personal de la Persona sobre en qué célula quiere servir. |
| D31 | Se descarta (para el MVP) un motor genérico de Formularios estilo Google Forms. Se usan entidades específicas por caso (Postulación, Solicitud de Bautismo, Solicitud de Discipulado, Inscripción a Evento), pero todas comparten una forma base consistente (persona_id, estado, fecha, revisado_por + campos propios). | Prioriza velocidad para el MVP sin cerrar la puerta a migrar a un motor genérico más adelante con bajo costo, gracias a la consistencia. |
| D32 | El primer paso de Vida Nueva (Flujo 3) pasa a ser una Solicitud de Discipulado in-app, ya no "fuera de la app". | Consistencia con el resto de los procesos (Bautismo, Vida de Servicio, Ministerio) que también arrancan con una solicitud dentro del sistema. |
| D33 | Evento tiene dos flags configurables por el Admin al crearlo: `requiere_inscripcion` y `requiere_aprobacion` (esta última solo si la primera es true). | Da flexibilidad: algunos eventos son solo informativos, otros necesitan anotarse, y de esos, algunos necesitan revisión (ej. cupo limitado) y otros no. |
| D34 | El público objetivo de un Evento (ej. "solo mujeres") es un campo de texto informativo, sin validación técnica de quién se inscribe. | Se confía en que la persona respete la indicación; no vale la pena construir validación de género/edad para esto en el MVP. |
| D35 | Un menor puede iniciar sesión una vez que el Admin/Discipulador pre-carga su cuenta (con el email que va a usar en el SSO) tras obtener autorización del tutor fuera de la app. El sistema reconoce ese email contra el registro existente en estado `activa` y lo deja entrar, sin repetir la validación de edad del Flujo 2. | Evita construir un sistema de autenticación paralelo para menores; reutiliza el mismo SSO, pero con el registro ya vetted por un humano. |
| D36 | El alta manual de un menor puede originarse tanto de un intento previo (`pendiente_tutor`) como crearse desde cero, sin intento previo. | Cubre ambos casos reales: el menor que probó solo, y el que el Discipulador ya conoce por otro medio. |
| D37 | Ninguna entidad de catálogo (Sede, Curso, Ministerio, Célula, Evento) se elimina definitivamente desde la app — todas usan soft delete vía un flag `activo`. | Preserva el historial de todo lo que las referencia (Grupos, Inscripciones, Postulaciones); más simple de construir que dos caminos (borrar/desactivar) separados. |
| D38 | Al desactivar un registro con datos relacionados activos (ej. Curso con Grupos en curso), el Admin debe confirmar escribiendo el nombre exacto del registro. Sin datos relacionados, alcanza una confirmación simple. | Agrega fricción solo cuando la acción afecta a personas reales, evitando desactivaciones accidentales de alto impacto. |
| D39 | Grupo tiene un mecanismo de finalización en dos pasos, común a Vida Nueva y Vida de Servicio: el Líder/Discipulador propone (`propuesta_finalizacion`), el Admin confirma (`estado = finalizado`). Al confirmarse, las Inscripciones `activa` pasan a `completada`. | Da control final al Admin sin perder la agilidad de que quien está en el día a día (Líder/Discipulador) inicie el proceso. |
| D40 | Solo en Vida de Servicio, al completarse la Inscripción se activa automáticamente `Persona.apto_ministerio = true`. En Vida Nueva no, porque ese proceso habilita el paso a Vida de Servicio, no a Ministerio. | Resuelve de forma automática y correcta el flag, evitando que el Admin tenga que revisar caso por caso quién terminó. |
| D41 | La asistencia a Vida de Servicio la puede registrar cualquier Líder asignado al Grupo, o el Admin — sin responsable fijo por semana. | Igual criterio que la carga de Contenido (D27); refleja que distintas personas rotan en la puerta. |
| D42 | La baja por exceso de faltas (más de 2) nunca es automática — el sistema solo alerta, la decisión de dar de baja (o hacer una excepción) es siempre manual del Líder/Admin. | Permite excepciones legítimas sin que el sistema fuerce una regla rígida. |
| D43 | Inscripción distingue dos motivos de no completar un Grupo: `dada_de_baja` (decisión administrativa, ej. faltas) y `abandono` (decisión de la propia Persona). Ninguno de los dos activa "Apto para Ministerio". | Permite reportar a futuro cuánta gente abandona por decisión propia vs. se da de baja, sin mezclar ambos motivos. |
| D44 | "Vida Nueva Grupal" es un segundo registro de Curso (tipo `grupal`, mismo nombre "Vida Nueva"), no una entidad nueva ni una variante técnica del mismo Curso. Usa la misma modalidad `seguimiento_por_encuentros` y la misma regla de asistencia/faltas que Vida de Servicio, y el mismo rol "Discipulador" (no un rol nuevo). | El campo `Curso.tipo` (individual/grupal) ya estaba pensado para esto desde la Sesión 3; no hace falta ampliar el modelo. |
| D45 | Encuentro se generaliza como el registro universal de "una reunión que ocurrió" para cualquier Grupo (no solo discipulado). Asistencia pasa a referenciar Encuentro en vez de Item de Cronograma. | Vida Nueva Grupal necesita asistencia pero no tiene Cronograma; separar "reunión que pasó" de "contenido digital liberado" resuelve el caso general sin duplicar modelos. |
| D46 | Se crea un documento de Roadmap de Producto (`08-roadmap-producto.md`) que separa Fase MVP / Fase 2 / Backlog, como visión completa del proyecto. El alcance del MVP pasa a ser un subconjunto de ese roadmap, no un techo fijo. | Sugerencia de un líder de la iglesia: presentar el proyecto completo, no solo el recorte inicial, para transmitir la visión completa además de lo ya construido. |
| D47 | Notificaciones push se incluyen en el MVP (no en Fase 2 como se había planteado inicialmente). Requiere convertir la app en PWA. | Decisión del autor tras evaluar la funcionalidad; resuelve directamente el problema original (enterarse de novedades sin depender de WhatsApp). |
| D48 | Las notificaciones manuales del Admin permiten elegir alcance: `todos`, un Grupo específico, o un Ministerio específico. | Da flexibilidad sin construir un segmentador complejo — se apoya en relaciones que ya existen (Inscripción, Postulación). |
| D49 | Se arranca con 3 disparadores automáticos: `contenido_liberado`, `solicitud_actualizada` (aplica a Postulación, Solicitud de Bautismo, Solicitud de Discipulado e Inscripción a Evento), y `evento_proximo` (este último requiere un proceso programado, no solo reacción a una acción). | Cubre los tres casos de uso reales mencionados por el usuario desde el principio. |
| D50 | Se incorpora un brainstorm amplio de funcionalidades futuras al roadmap (feeds de redes, "Mi camino", pedidos de oración, directorio, calendario unificado, voluntariado puntual, Escuelita, dashboard, auditoría, gestión de contenido institucional, exportación de datos, buscador general, offline básico), todas en Fase 2. | Da una visión completa del proyecto para presentar a los pastores, sin comprometer el MVP a construir todo esto ahora. |
| D51 | La disponibilidad del Discipulador combina un toggle manual (`disponible_discipulado`, nunca automático) con Bloqueos de Disponibilidad por rango de fechas (ej. vacaciones), que se levantan solos al pasar la fecha. El Admin filtra por ambos criterios al asignar un nuevo discipulado. | Evita sobrecargar discipuladores y evita que alguien se olvide de "reactivarse" manualmente tras sus vacaciones. |
| D52 | El material de Vida Nueva puede digitalizarse a futuro (Cronograma/Contenido opcional, ya soportado desde D24) sin necesitar cambios nuevos al modelo — queda como posibilidad activable cuando la iglesia lo decida, no como tarea de esta sesión. | El modelo ya estaba preparado para este caso; no hace falta ninguna decisión adicional ahora. |
| D53 | El registro inicial (Flujo 2) se amplía con: apellido (separado de nombre), estado civil (opciones predefinidas: soltero/a, casado/a, en concubinato, viudo/a, divorciado/a, separado/a), profesión, y tiempo congregándose (rango predefinido). Todos obligatorios desde el arranque. | Cubre de entrada los datos que hoy se piden por separado en el formulario físico de Bautismo, evitando pedirlos dos veces. |
| D54 | Evento admite `cupo` opcional con `permite_lista_espera` configurable: si se llena, según el flag, bloquea nuevas inscripciones o las pasa a `lista_espera`. | Cubre tanto Eventos sin límite práctico como Campamentos con capacidad real, sin forzar un único comportamiento. |
| D55 | Se agrega la entidad Pago (monto, medio de pago, comprobante adjunto, estado de verificación) para Eventos con `costo` definido (ej. Campamentos). No procesa pagos reales — es un registro manual verificado por el Admin, igual que el seguimiento actual en papel/Excel. | Cubre el caso de Campamentos con costo sin necesitar integrar una pasarela de pago real, que excede el alcance de este proyecto. |
| D56 | Al crear un Evento con `requiere_inscripcion = true`, el sistema genera un código QR que lleva directo al formulario de inscripción (reemplaza el QR a Google Forms que hoy se usa en el culto). | Resuelve directamente un caso de uso real mencionado por el usuario, con bajo costo de implementación. |
| D57 | Escuelita y Grupos de Extensión quedan en Fase 2, cada uno con nota de que requiere su propia sesión de diseño antes de especificarse (roles, entidades y flujos propios, no triviales). | Mantiene el MVP acotado sin perder de vista la visión completa del proyecto. |
| D58 | Se agrega cancelación de Inscripción a Evento por la propia Persona, con promoción automática del primero de la lista de espera al estado correspondiente + notificación. | Sin esto, la lista de espera (D54) no cumplía su función — nadie liberaba lugar. |
| D59 | Notificación (automática) guarda `entidad_relacionada_tipo` e `id`, para poder llevar a la Persona directo a lo que la generó. | Mejora de usabilidad básica; sin esto una notificación es un callejón sin salida. |
| D60 | No se permite más de una Solicitud/Postulación del mismo tipo en estado `pendiente` por Persona al mismo tiempo. | Evita duplicados accidentales y confusión en la revisión del Admin. |
| D61 | El Admin tiene una vista de perfil unificada por Persona (roles, historial de Inscripciones/Postulaciones/Solicitudes, Relaciones Familiares) en una sola pantalla. | Es la vista más usada por un Admin real; tenerla fragmentada por módulo es poco práctico. |
| D62 | Se agrega un listado de cumpleaños del mes en el back office, calculado desde `fecha_nacimiento` (sin entidad nueva). | Alto valor pastoral con costo de implementación casi nulo. |
| D63 | Se agrega la entidad Relación Familiar (Persona↔Persona, con tipo de relación). | Sienta base para agrupar notificaciones por familia y para el vínculo padre-hijo que necesitará Escuelita (Fase 2). |
| D64 | La Persona puede editar sus propios datos de contacto y otros campos no críticos desde "Mi perfil", pero no `fecha_nacimiento` ni `email` (requieren contactar al Admin). El rol Pastor se revisó y se mantiene con acceso de solo lectura a todo, incluyendo datos de contacto — se considera parte legítima de su función pastoral. | Balance entre autonomía de la Persona y protección de datos sensibles a validaciones ya hechas (edad) o a la identidad de login. |
| D65 | Se investigaron sitios de iglesias evangélicas argentinas (Rey de Reyes, Catedral de la Fe, Casa de Dios) y se revisó el sitio actual (desactualizado) de Vida Sobrenatural. Confirma que el MVP ya cubre lo esencial que otras iglesias ofrecen (bienvenida a nuevos, cursos, liderazgo, contacto), y que Notificaciones push y el seguimiento de progreso por Persona son diferenciales reales frente a sitios puramente informativos. | Valida el enfoque del proyecto con datos de mercado reales, no solo con la experiencia personal del autor. |
| D66 | Se suma "En qué creemos" (declaración institucional estática) al MVP, dentro de Bienvenida. | Contenido de bajísimo costo, presente en sitios de referencia, ausente en nuestro modelo hasta ahora. |
| D67 | Se agrega una versión estática de "Ofrendas" al MVP (alias/CBU como texto informativo, sin procesar pagos). La integración con Mercado Pago u otro servicio de pago real queda en Fase 2. | Las donaciones son una expectativa casi universal en sitios de iglesias; una versión estática tiene costo casi nulo y cubre la necesidad inmediata. |
| D68 | Se agregan métricas básicas al MVP para el Admin (conteo de Personas activas, distribución por tiempo de congregación, por Sede) — separado del dashboard analítico completo (tasas de conversión/abandono), que sigue en Fase 2. | El usuario identificó valor concreto en esta información simple, con bajo costo de implementación frente al dashboard completo. |
| D69 | La cancelación de una Inscripción a Evento puede hacerla la propia Persona desde la app, o el Admin manualmente desde el back office. Ambos caminos producen el mismo resultado (incluida la promoción desde lista de espera). | No toda baja depende de que la Persona use la app — muchas veces avisan por otro canal (WhatsApp, en persona) y el Admin necesita poder registrarlo igual. |
| D70 | Se agrega el campo `genero` a Persona, obligatorio desde el registro inicial. | Necesario para mostrar correctamente "Pastor/Pastora" y para el futuro matching de Grupos de Extensión (Fase 2), que ya requería este dato. |
| D71 | El Discipulador es, por norma general, un líder ya reconocido de la iglesia — no cualquier Miembro registrado. No se modela como una restricción técnica nueva; queda a criterio del Admin al asignar (ver D25). | Refleja cómo funciona hoy en la práctica; no amerita una regla dura en el sistema mientras el Admin sea quien asigna manualmente. |
| D72 | El campo `alcance` de Notificación deja de ser exclusivo de las manuales — se unifica para todas: las automáticas también tienen un alcance (`grupo` para `contenido_liberado`, `evento` para `evento_proximo`, `persona` para `solicitud_actualizada`), solo que lo determina el disparador en vez de elegirlo el Admin. | Consistencia de modelo: toda Notificación tiene un destinatario definido de la misma forma, sea manual o automática. |
| D73 | Se agrega un cuarto disparador automático, `recordatorio_inscripcion`: si el Evento tiene `dias_anticipacion_recordatorio` configurado (opcional, por Evento), se envía un recordatorio con alcance `todos` a esos días de anticipación, para incentivar a quien todavía no se inscribió. | Sin segmentación técnica de "a quién le interesa" un Evento, la única forma de llegar a quien podría anotarse es enviarlo a todos; se deja configurable por Evento para que el Admin lo use solo donde tenga sentido. |
| D74 | Vida de Servicio requiere haber completado Vida Nueva (individual o grupal, cualquiera cuenta — modelado vía `Curso.categoria` + `prerequisito_categoria`). El botón de solicitud queda bloqueado si no se cumple. El Admin puede destrabar esto marcando una **Completitud Manual** para la Persona, sin pasar por un Grupo/Inscripción real. | Refleja el proceso real de la iglesia, con una vía de excepción para casos que no encajan en el flujo normal (ej. alguien que hizo Vida Nueva en otra congregación, o antes de que existiera el sistema). |
| D75 | Stack técnico definido: NestJS (backend) + Next.js/React (frontend) + PostgreSQL + Prisma (ORM) + NextAuth.js (SSO). Almacenamiento de archivos local en desarrollo, detrás de una capa de abstracción para migrar a S3-compatible después. Hosting de producción pospuesto deliberadamente — se desarrolla en local primero. | Preferencias técnicas de la desarrolladora del proyecto; evita comprometer un hosting real (y sus planes gratuitos limitados) antes de tener algo para mostrar. |
| D76 | Arquitectura de 3 aplicaciones en monorepo (pnpm + Turborepo): `apps/web` (PWA, usuario final), `apps/backoffice` (Admin/Discipuladores/Líderes), `apps/api` (NestJS, única puerta a la base de datos), con `packages/shared-types` compartiendo el modelo de datos entre las tres. | Las 3 apps comparten el mismo modelo de datos; un monorepo con tipos compartidos evita desincronización entre frontend y backend, con TypeScript avisando apenas algo deja de coincidir. |
| D77 | Se suman al stack: Tailwind CSS (estilos), shadcn/ui (componentes UI, compartidos vía `packages/ui`), y Swagger/OpenAPI (`@nestjs/swagger`, documentación de API autogenerada desde los mismos decoradores). | Evita reinventar componentes de UI básicos; Tailwind facilita aplicar la identidad visual de la Sesión 6 de forma centralizada; Swagger da documentación de API casi gratis y puede alimentar la generación del cliente TypeScript compartido. |
| D78 | Se pide consentimiento explícito de almacenamiento de datos personales desde el registro inicial (Fase Bienvenida), en vez de posponerlo hasta un lanzamiento real. | Al revisar el spec de Bienvenida se identificó que ya se manejan datos sensibles desde el día uno (afiliación religiosa vía D5, datos de menores vía D4/D21). Se decide no esperar a tener la política de privacidad completa para dar este primer paso, de bajo costo de implementación. Ver también la nueva sección de pendientes de privacidad en `06-preguntas-abiertas.md`. |
